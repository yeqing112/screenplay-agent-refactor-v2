# 产品重构实施方案

## 1. 文档目标

本方案用于把 [产品重构蓝图.md](D:\Work\Project\screenplay-agent-refactor-v2\docs\产品重构蓝图.md) 和当前前端原型落成可执行的产品重构路线。

本方案回答四个问题：

1. 重构后的正式产品结构是什么
2. 每个一级模块负责什么
3. 模块之间如何串成完整主链路
4. 实施时先做什么、后做什么、哪些必须保持兼容

## 2. 重构目标

项目当前的主要问题不是功能太少，而是产品结构混杂：

- 起点不清晰，内容准备缺失
- 改编方向不是项目级约束
- 剧本模块没有独立产品位
- 分镜、资产、QA、任务、导出已存在但没有被统一编排
- 页面职责过重，主链路不够可见

本次重构的目标是把系统重构为一个完整的 AI 短剧生产操作系统，形成以下正式主链路：

`内容准备 -> 改编方向 -> 剧本工作台 -> 镜头工作台 -> 资产中心 -> QA 修复 -> 导出中心`

项目控制台、任务中心、模型管理作为全局支撑模块。

## 2.1 2026-08-15 剧本链路实施原则调整

从 2026-08-15 开始，剧本链路的实施原则新增一条高优先级约束：

### 不再继续扩大启发式修补面

最近的真实样本回归已经证明，只继续在 `QA title / description -> rewrite directive` 上堆更多命中规则，虽然能短期覆盖新问题，但会带来三个副作用：

- 测试越来越多，但真实样本分数不稳定
- Rewrite 容易引入新的二次连续性错误
- 规则越来越依赖当前样本表述方式，迁移性变差

因此，后续剧本整改不再把“继续增加标题触发规则”当作主路径，而改为：

### 先做结构化中间层，再做剧本编译

剧本生成需要逐步过渡为：

1. 生成人物外显层和隐藏层
2. 生成场景目标与局势变化
3. 生成证据链与入画/来源/回收点
4. 生成集尾钩子增量
5. 再编译成最终剧本

也就是说，后续所有脚本重构、QA 重构、Rewrite 重构，都要优先问自己：

- 我是在补一个样本，还是在补一个结构字段？
- 这个修复是否能跨题材复用？
- 这个问题是否应该在生成前就被结构约束，而不是生成后再追着修？

## 2.2 2026-08-16 剧本生产链路实施升级

从 2026-08-16 开始，剧本链路的工程实施不再把“继续扩充 Rewrite 约束”当作主建设路径，而改为先落中间结构，再落编译器。

### 新的最小工程落地顺序

1. 定义 `Story Fact Sheet`
2. 定义 `Scene Execution Cards`
3. 定义 `Screenplay Compiler` 输入契约
4. 定义 `Structure QA` 校验口径

### 这意味着什么

后续开发时，遇到新的剧本问题，必须先问：

1. 这是事实层缺口吗？
2. 这是场景执行层缺口吗？
3. 这是编译层偏移吗？
4. 它是否应该新增为结构字段，而不是新的启发式命中规则？

### 第一阶段开发边界

第一阶段先不强行一次性替换所有旧路径，而是采用“新结构接线、旧路径兼容”的方式：

- foundation 层先补出 `story_fact_sheet`
- generation brief 层先补出 `scene_execution_cards`
- execution plan 层先显式区分 `fact_generation / scene_execution / screenplay_compile / structure_qa`
- rewrite / qa 后续逐步改为优先消费这些字段

## 3. 正式产品结构

### 3.1 项目控制台

职责：

- 查看项目总体状态
- 查看分集进度
- 查看各阶段 readiness
- 查看 QA 阻塞
- 查看任务全景
- 管理导出状态

目标用户：

- 导演
- 制片
- 项目管理

关键指标：

- 哪一集最阻塞
- 哪一阶段最薄弱
- 哪些任务失败
- 哪些集可以交付

### 3.2 内容准备

职责：

- 导入长篇小说
- 直接录入短篇小说
- 进行内容清洗和切章确认
- 建立原文版本基线

必须支持：

- 文件上传
- 粘贴录入
- 短篇新建
- 章节确认
- 内容备注
- 进入改编方向评估

### 3.3 改编方向

职责：

- 评估原著适合的短剧方向
- 生成 2-3 个候选改编方向
- 由用户选择主方向
- 锁定项目级改编基线

每个改编方向卡至少包含：

- 目标赛道
- 目标受众
- 一句话卖点
- 改编强度
- 节奏策略
- 保留内容
- 强化内容
- 风险提示

### 3.4 剧本工作台

职责：

- 组织分集剧本
- 管理场次
- 管理剧本版本
- 管理剧本 QA
- 进行进入分镜前放行

必须承载：

- 分集剧本列表
- 场次结构
- 脚本片段
- 单集目标
- 进入分镜前检查
- 剧本 QA 和重写

### 3.5 镜头工作台

职责：

- 管理单集镜头生产
- 编译静态提示词和运动提示词
- 管理分镜图和视频版本
- 管理镜头级 QA 修复

必须承载：

- 镜头列表
- 镜头 readiness
- 资产引用
- prompt version
- 图版 / 视频版
- 采纳状态

### 3.6 资产中心

职责：

- 管理人物、场景、道具和参考图
- 处理造型变体
- 提供资产与镜头的引用关系

必须承载：

- 人物定妆
- 人物变体
- 场景资产
- 道具资产
- 参考图预览 / 删除 / 默认设置
- 反查影响镜头

### 3.7 QA 修复工作台

职责：

- 汇总脚本、分镜、资产、视频问题
- 把问题转为修复动作
- 记录修复过程和回测结果

必须承载：

- 问题列表
- 问题类型
- 严重等级
- 推荐修复动作
- 关联对象跳转
- 生命周期状态

### 3.8 任务中心

职责：

- 汇总所有异步和批量任务
- 提供失败恢复和重试入口
- 对齐任务状态与生产状态
- 保留真实创意任务的恢复谱系与重发历史

### 3.9 导出中心

职责：

- 交付前 readiness 检查
- 导出按集交付包
- 输出状态摘要和版本号

### 3.10 模型管理

职责：

- 管理文本 / 图像 / 视频模型
- 管理供应商差异
- 管理模型能力配置

## 4. 重构实施原则

### 4.1 先结构，后细节

优先把一级模块和主链路立住，再做局部功能深化。

### 4.2 先入口，后中段，最后交付

先补“内容准备”和“改编方向”，再稳定剧本和分镜工作台，最后完善 QA、任务和导出。

### 4.3 先可见，后智能

先解决页面结构和状态可见性，再继续提升 LLM 编译质量、资产关联精度和自动修复能力。

### 4.4 先兼容，后收敛

短期继续兼容现有模型和 `asset_links` 数据结构；中期再逐步收敛接口语义和领域模型。

## 5. 技术与实现边界

### 5.1 现阶段保留的基础

- 现有 `Book` / `StoryboardShot` / `Visual*` / `PromptVersion` / `QAIssue` 模型
- 现有 pipeline / agent 能力
- 现有前端 production/prototype 模式

### 5.2 现阶段必须新增或明确的能力

- 内容准备入口与状态
- 改编方向对象和锁定状态
- 剧本放行状态
- 镜头 readiness 体系
- 资产预览与删除
- QA 转修复动作
- 导出前 readiness 检查

### 5.3 现阶段禁止事项

- 不允许继续把所有逻辑塞进单一 `ProductionMode`
- 不允许跳过“内容准备”和“改编方向”直接设计后面页面
- 不允许做只对单一供应商生效的硬编码模型接入

## 6. 模块依赖关系

### 6.1 上游到下游依赖

1. 内容准备
2. 改编方向
3. 剧本工作台
4. 镜头工作台
5. 资产中心
6. QA 修复
7. 导出中心

### 6.2 横向支撑模块

- 项目控制台：总览
- 任务中心：执行与恢复
- 模型管理：模型配置与能力描述

## 7. 实施产出要求

每一阶段实施完成后，至少要同步产出：

1. 页面或模块实现
2. 对应接口或兼容层
3. 阶段验收记录
4. 文档更新

## 8. 成功标准

本轮产品重构完成后，至少应达到：

1. 用户可以从“上传小说/添加短篇”开始完整进入系统
2. 用户可以显式确认改编方向，而不是隐含写死
3. 剧本、分镜、资产、QA、导出形成完整闭环
4. 用户无需理解 pipeline 也能知道下一步做什么
5. 所有核心媒体和提示词均可追踪版本
6. QA 问题都有修复入口

## LibTV 化融合实施补充（2026-07-28）

本项目后续实施方向调整为“生产内核 + 创作画布”的融合架构。

实施原则：

1. 当前正式工作台继续承担生产内核，不做推翻式重写。
2. 新增 `创作画布 Beta` 作为并行入口，先只读映射真实项目数据。
3. 画布节点执行必须复用现有任务中心、模型管理、资产中心和镜头工作台。
4. 画布输出统一进入 `Artifact / ArtifactVersion` 语义，并可回写现有分镜图、视频、参考图和导出包。
5. 画布数据必须保存 revision 和执行输入快照，避免生成过程不可复现。
6. 旧项目打开时自动生成默认生产画布，不要求用户迁移数据。

# 2026-07-21 分镜编译关键资产保底回填与修复上下文增强记录

## 本轮目标

继续沿蓝图推进分镜提示词编译治理，优先解决两个会误伤生产判断的问题：

1. 提示词里其实已经提到关键绑定资产，但 `used_assets` 漏报，导致 QA 与工作台出现假阴性告警
2. 自动修复虽然会重编译，但没有把“必须补入哪些视觉事实、必须保留哪些关键资产”整理成更硬的结构化修复指令

## 本轮实现

### 1. 关键绑定资产保底回填

文件：

- `api/server.py`

新增逻辑：

- `_is_critical_bound_asset_for_usage(...)`
- `_hydrate_used_asset_from_bound_item(...)`
- `_supplement_used_assets_from_prompt_mentions(...)`

规则：

- 对场景、人物、以及 `importance = high` 的道具，如果它们已经是正式绑定且存在参考图
- 并且静态提示词或运动提示词里已经明确提到该资产名，或提到对应 `reference_token`
- 则即使 LLM 没有把它写入 `used_assets`，系统也会把它补回本次编译结果

这个修复的边界是克制的：

- 只补“关键绑定资产”
- 只补“提示词里已经明显提到”的资产
- 不会把完全没写到的资产硬塞进 `used_assets`

### 2. 修复上下文增强

文件：

- `api/server.py`

新增逻辑：

- `_parse_failed_check_detail(...)`
- `_build_repair_visual_fact_targets(...)`
- `_build_repair_required_used_assets(...)`

修复上下文现在会额外带出：

- `repair_request.visual_fact_targets`
  - 明确列出哪个资产缺了哪些视觉事实
  - 并给出 `min_facts_to_include`
- `repair_request.required_used_assets`
  - 当 `critical_bound_asset_usage` 失败时，明确列出本轮必须保留在 `used_assets` 中的关键绑定资产

这意味着自动修复不再只是拿到一堆 warning 文案，而是拿到更结构化、可执行的修复目标。

### 3. 测试文件清理

文件：

- `tests/test_storyboard_prompt_repair_context.py`

处理：

- 将历史乱码测试文件重写为干净 UTF-8 版本
- 补充新断言，覆盖修复上下文中的新增结构化字段

## 本轮结论

本轮已经把分镜编译链往生产真相又推进了一步：

1. “提示词已写到，但 `used_assets` 漏报”的假阴性开始被系统自动收敛

本轮重构的目标不是再加零散功能，而是把项目重构成一套可运营、可追踪、可修复的 AI 短剧生产操作系统。

## 2026-08-15 剧本生成整改补记

### 这轮调整要解决什么

最近一轮 `Production Skill + QA + Rewrite` 的推进里，系统已经开始出现“规则越来越多、样本分数却不稳定”的信号。

这说明问题不再只是规则缺失，而是剧本生成机制本身还不够结构化：

- 仍然允许模型在大段自由文本里临场发挥
- QA 虽然能报问题，但很多问题仍在通过样本导向的启发式触发词回修
- Rewrite 能修局部，但不够稳定地继承“人物外显层 / 证据链 / 场景目标 / 钩子增量”

因此，从 2026-08-15 开始，剧本生产进入新的整改原则：

### 新原则：停止继续堆启发式规则，转向结构化生成

后续剧本整改不再以“针对某个真实样本再补一条命中规则”为主，而改为重建剧本生成骨架。

核心方向：

1. 先生成结构，再编译成剧本  
   先生成：
   - 人物外显层
   - 人物隐藏层
   - 场景目标
   - 证据链
   - 集尾钩子增量

   再把这些中间结构编译成可拍剧本，而不是直接让模型自由写整集。

2. QA 以结构检查为主，不再主要依赖标题关键词命中  
   QA 的重点应转为：
   - 证据首次入画点
   - 证据来源点
   - 证据回收点
   - 人物外显层连续性
   - 场景结尾新增变量

3. Rewrite 以结构回写为主，不再继续扩大样本导向补丁库  
   现有通用规则可继续保留，但后续新增规则必须优先证明自己属于：
   - 跨题材稳定成立
   - 可落成结构字段
   - 可被 QA 和 Rewrite 共用

### 允许保留的现有成果

以下已有沉淀应保留，因为它们已经具备通用性：

- 证据先入画再上台词
- 懒散人物执行动作时保留人设
- 同一线索二次出现必须带来新增信息
- 钩子必须有信息增量
- 心理状态需要外化为可拍动作
- 危险中的闪回不能抽空当前压力

### 后续不再鼓励的做法

- 围绕某个样本标题继续增加大量 `if title contains ...`
- 为单个剧本问题继续扩写更细的触发词表
- 通过越来越长的 prompt 列表去硬压模型记住所有特例

### 这次整改的验收目标

剧本链路后续不只看“有没有过测试”，还要看：

1. 同一真实样本连续两轮 Rewrite + QA 的分数是否稳定，不再大起大落
2. 新增 QA 问题是否主要映射到结构字段缺口，而不是提示词命中缺口
3. Rewrite 是否更少引入“二次改坏”的新连续性错误
4. 新规则是否可以跨样本复用，而不是只对当前样本有效

## 2026-08-16 剧本生产 Skill 重构补记

### 这次正式废弃什么

从 2026-08-16 开始，`直接根据 Production Skill + QA + Rewrite prompt 重写整集剧本` 不再视为剧本链路的长期主路径。

它可以继续作为兼容回退路径存在，但不再作为生产级收敛方案。

原因已经很明确：

- 它本质上仍然让模型在自由文本里做过多临场决策
- QA 只能在结果层追错，无法稳定约束中间事实
- Rewrite 即使能修通一次，也容易在下一轮引入新的连续性错误
- 规则会越来越像“问题库”，而不是“生产系统”

### 新主路径：事实层 -> 场景执行层 -> 剧本编译层

后续 Script Skill 的正式主链路改为三层编译：

1. `Story Fact Sheet`
2. `Scene Execution Cards`
3. `Screenplay Compiler`

#### 1. Story Fact Sheet

先生成整集不可跳过的结构化事实，而不是先写剧本文本。

至少包含：

- `character_public_layers`
- `character_hidden_layers`
- `character_state_transitions`
- `core_props`
- `prop_state_chain`
- `evidence_chain`
- `helper_motives`
- `spatial_mechanics`
- `hook_deltas`

这一层回答：

- 谁表面上是什么人
- 谁实际上在隐藏什么
- 哪个关键物证从哪里来、被谁拿过、最后在哪里
- 哪个帮助行为为什么会发生
- 哪个机关到底怎么开
- 结尾到底新增了什么信息

#### 2. Scene Execution Cards

按场次生成执行卡，不直接让模型跨整集自由发挥。

每场至少包含：

- 开场角色状态
- 开场物件状态
- 本场目标
- 本场冲突
- 本场必须出现的视觉证明
- 本场人物外显层动作
- 本场隐藏层泄露点
- 本场结束状态
- 下一场承接条件

这一层回答：

- 这场戏为什么存在
- 这场戏结束后系统状态发生了什么变化
- 哪个动作是角色公开面
- 哪个细节是隐藏面泄露
- 哪个镜头负责证明某个事实

#### 3. Screenplay Compiler

最终剧本不再直接生成，而是从前两层结构编译出来。

编译器必须遵守：

- 不得改写事实层已锁定的关键物证链
- 不得跳过场景执行卡中的必需视觉证明
- 不得在没有触发器的情况下让角色突然反转
- 不得让机关操作超出事实层已声明的空间结构

### QA 也要同步换轨

后续 QA 的主责不是继续报“哪里看起来不对”，而是检查：

- 事实层是否闭合
- 场景执行层是否完整
- 编译结果是否忠实继承结构

也就是说，QA 应优先回答：

1. 哪个事实字段缺失
2. 哪个场景卡没有兑现
3. 哪个编译结果背离了事实层

### 第一阶段落地范围

第一阶段不追求一次性替换整条剧本链路，而是先做最小可运行主干：

1. 在 Script Skill foundation 中新增 `story_fact_sheet`
2. 在 Script Generation Brief 中新增 `scene_execution_cards`
3. 在 Execution Plan 中新增 `fact_generation -> scene_execution -> screenplay_compile -> structure_qa`
4. Rewrite / QA 优先消费这些结构，而不是继续单靠启发式 issue 标题

### 第一阶段验收标准

1. 新结构已进入正式文档、规则文档和代码对象
2. `build_script_skill_foundation` 可稳定返回 `story_fact_sheet`
3. `build_script_generation_brief` 可稳定返回 `scene_execution_cards`
4. `build_script_skill_execution_plan` 明确包含新的结构化编译阶段
5. 后续真实样本整改优先围绕结构字段缺口进行，而不是继续扩写标题触发规则

## Product Positioning

### 产品定位

把该项目定义为：

“面向 AI 短剧生产团队的资产驱动型分镜生产与交付平台”

它不是：

- 单纯提示词生成器
- 纯小说改编工具
- 纯生图/生视频调用器

而是：

- 有项目管理能力
- 有资产一致性能力
- 有镜头生产能力
- 有质检修复闭环
- 有交付组织能力

### 目标用户

1. 短剧导演 / 制片：关心整集进度、风险、交付状态
2. 分镜编辑 / 视觉策划：关心镜头提示词、参考图、版本、采纳
3. 美术 / AI 制图执行：关心人物、场景、道具资产与一致性
4. 运营 / 项目管理：关心批量任务、失败重试、导出包

### 核心北极星指标

1. 单集从剧本到“可交付分镜包”的平均时长
2. 分镜图一次通过率
3. 角色/场景一致性质检通过率
4. QA 问题闭环修复率
5. 导出包可直接交付率

## Information Architecture

### 1. 项目控制台

用于看全局，不处理细镜头。

应包含：

- 项目列表
- 项目概览卡
- 剧本阶段进度
- 分镜阶段进度
- 视觉资产准备度
- QA 阻塞数量
- 导出准备度
- 批量任务中心
- 模型与供应商配置入口

关键视图：

- `项目概览`
- `分集列表`
- `任务中心`
- `质检中心`
- `导出中心`
- `模型管理`

### 2. 镜头工作台

用于处理单集、单镜头，是未来最高频页面。

应围绕单集展开四栏式结构：

- 左侧：集/场/镜头树
- 中间：镜头卡流或镜头编排区
- 右侧：当前镜头详情与操作面板
- 顶部：阶段状态、批量动作、筛选器

镜头工作台的核心子视图：

1. `镜头列表视图`
2. `资产关联视图`
3. `提示词编译视图`
4. `出图/出视频版本视图`
5. `QA 修复视图`

### 3. 资产中心

不是只展示提示词，而是管理“可被镜头引用的稳定资产”。

资产对象：

- 人物
- 人物定妆变体
- 场景
- 道具
- 参考图
- 分镜图
- 分镜视频

每个资产都必须具备：

- 来源
- 作用范围
- 关联镜头
- 提示词来源
- 版本历史
- 是否采纳
- 预览能力
- 删除/替换能力

7. 批量重编译 / 批量重试接口
8. 导出包生成接口

## Product Refactor Plan

### 一、重构主链路：从流水线思维改为生产工作流思维

现状问题：

- 用户像在“跑一条技术管线”
- 看得到阶段，看不到产物成熟度
- 看得到结果，看不到缺什么

目标形态：

- 每一集都显示“是否可进入下一阶段”
- 每一镜都显示“缺资产 / 缺提示词 / 缺分镜图 / 缺视频 / 有 QA 阻塞”
- 用户永远知道下一步动作

实施要求：

- 把“脚本准备 / 分镜 / 视觉 / QA / 导出”统一成阶段状态机
- 增加每集 readiness score
- 增加每镜头 checklist
- 批量操作只针对“未完成项”和“阻塞项”

验收标准：

- 用户打开项目 10 秒内能判断哪一集最阻塞
- 用户进入单集 10 秒内能判断哪几个镜头不能出图
- 页面存在清晰“下一步建议动作”
- 不再依赖用户自己理解后端 pipeline 顺序

### 二、重构分镜系统：从“提示词字段”升级为“镜头生产单元”

现状问题：

- 静态提示词和运动提示词质量不稳定
- 提示词缺少资产引用
- 镜头缺少版本、来源、修复上下文

目标形态：

- 一个镜头是完整生产单元，不只是两段 prompt
- 每次编译都产出结构化 prompt version
- 编译必须引入：
  - 剧情上下文
  - 镜头意图
  - 人物定妆/服装变体
  - 场景参考
  - 道具参考
  - 负面约束
  - 运动策略

实施要求：

- LLM 参与静态/运动提示词编译
- prompt 产物结构化存储
- 支持锁定版本、重编译、人工修订、回滚
- 支持在 prompt 中引用资产，不建议只暴露 `@姐姐(URL)` 这种文本语法给终端用户，推荐产品层使用：
  - `引用资产` 选择器
  - 结构化 `reference_asset_ids`
  - 渲染层可显示为 `@角色名`、`@场景名`
- 如果模型支持多图参考，则按 asset ids 传引用列表
- 如果模型只支持文本 prompt，则在编译阶段注入结构化资产摘要

验收标准：

- 任一镜头都能看到“本次提示词引用了哪些人物/场景/道具”
- 同一人物跨镜头换装时，提示词能稳定切换到对应定妆变体
- 重新编译不会覆盖旧版本
- 锁定版本后，批量编译默认跳过
- 质检问题能追溯到具体 prompt version

### 三、重构资产系统：从“提示词存在”升级为“资产可用”

现状问题：

- 人物/场景/道具有提示词，但并非真正可用资产
- 参考图可生成，但管理能力不完整
- 缺预览、删除、替换、采纳策略

目标形态：

- 所有资产先成为“可管理对象”，再参与分镜
- 资产系统支持从设定到引用再到替换的完整闭环

实施要求：

- 人物定妆必须支持“基础人设 + 当前镜头服装/状态变体”
- 每个参考图必须支持：
  - 预览
  - 删除
  - 查看来源 prompt
  - 查看引用镜头
  - 设为默认参考
- 资产与镜头之间提供引用关系图
- 在镜头侧能直接看出“本镜头使用的是哪一版角色参考图”

验收标准：

- 任意参考图都能预览内容
- 任意参考图都能删除，删除后相关镜头状态实时更新
- 同一角色可存在多套造型变体，并按镜头正确引用
- 从角色资产页能反查其影响的所有镜头
- 从镜头页能看到它当前绑定的所有静态资源

### 四、重构 QA：从报告系统升级为修复工作台

现状问题：

- QA 只告诉你哪里不好
- 没有“如何修复”
- 也没有和提示词、资产、版本联动

目标形态：

- 每条 QA 问题必须落到可修复动作
- QA 问题可以一键转任务
- 修复后可回测、可关闭、可追踪

实施要求：

- `QAIssue` 增加：
  - 问题类型
  - 影响范围
  - 推荐修复动作
  - 关联镜头
  - 关联 `prompt version`
  - 关联 `asset version`
- 提供修复动作模板：
  - 重新编译静态提示词
  - 重新编译运动提示词
  - 更换人物参考图
  - 更换场景参考图
  - 重新出图
  - 重新生成视频
- 支持问题状态流转：
  - `open`
  - `in_progress`
  - `resolved`
  - `wont_fix`

验收标准：

- 每条 QA 问题都能进入具体修复动作
- 修复后能记录“修了哪一版”
- QA 页面可以按问题类型、集数、镜头筛选
- 不再出现“发现问题但没有修复入口”的体验断裂

### 五、重构任务中心：从后台轮询升级为生产调度中心

现状问题：

- 任务存在，但产品上不可管理
- 批量编译、失败重试、阻塞恢复体验弱

目标形态：

- 所有生成动作进入统一任务中心
- 用户能管理队列、失败、重试、跳过、优先级

实施要求：

- 统一任务卡结构：
  - 任务类型
  - 目标对象
  - 输入摘要
  - 当前状态
  - 失败原因
  - 重试入口
- 对真实创意任务补齐恢复谱系：
  - 原任务号
  - 重发后的新任务号
  - 最近一次重发时间
  - 累计重发次数
- 任务动作要按状态显式收敛：
  - `queued/running` 优先刷新状态与继续回收
  - `error/not_found` 优先重新发起
  - `done` 优先回到对应工作台确认结果与采纳
- 支持批量任务：
  - 批量补齐参考图
  - 批量编译镜头 prompt
  - 批量生成分镜图
  - 批量视频生成
- 第一阶段可先用任务中心直连现有真实接口，形成“批量发起 -> 结果回到工作台 / 恢复链路”的轻量闭环，再逐步补统一批量任务模型
- 批量任务至少要保留最近一次执行摘要：
  - 执行动作
  - 成功 / 失败数量
  - 最近执行时间
  - 摘要说明
- 任务中心应能回看最近几次批量执行历史，而不只是覆盖上一条
- 长任务要有断点恢复与可见进度

验收标准：

- 任何生成失败都能在任务中心看到原因
- 失败任务可单独重试
- 批量任务不会因为单镜头失败导致全局假死
- 用户能清楚区分“排队中、执行中、成功、失败、跳过”

### 六、重构交付：从数据导出升级为交付包

现状问题：

- 输出很多，但还不像可交付成果
- 缺状态快照、版本封板、交付说明

目标形态：

- 一集一包，可直接给下游
- 导出不仅有内容，还有状态与说明

实施要求：

- 导出包至少包含：
  - 剧本版本
  - 分镜表
  - 当前采纳分镜图
  - 当前采纳视频
  - 角色/场景/道具参考图
  - QA 状态摘要
  - 交付时间与版本号
- 提供“仅导出已采纳资产”选项
- 提供“导出阻塞报告”选项

验收标准：

- 导出包能按集生成

## 补充蓝图：视觉资产多变体体系

### 补充目标

本轮蓝图新增一条统一约束：人物、场景、道具都不能再按“一个名字 = 一个资产”来设计，而必须统一升级为多变体视觉资产体系。

这项补充直接服务于以下真实生产问题：

- 同一人物跨集、跨剧情阶段、跨状态时，不能只靠一套定妆
- 同一场景在白天 / 夜晚 / 雨天 / 破坏后，不能共用同一版提示词与参考图
- 同一道具在完整 / 破损 / 使用中 / 污损状态下，不能仍然指向同一版资产
- 镜头编译必须引用具体可追踪的资产变体，而不是只引用主资产名或摘要文本

### 统一资产抽象

所有视觉资产统一采用以下四层模型：

1. `Asset Master`
   - 人物主档 / 场景主档 / 道具主档
   - 承载稳定识别信息
2. `Asset Variant`
   - 镜头真正引用的生产单元
   - 支持 `base_identity / episode_default / scene_variant / shot_variant`
3. `Reference Images`
   - 每个变体可挂载多张参考图
   - 区分候选、默认、锁定、补充细节图
4. `Shot Binding`
   - 镜头必须显式绑定到某个具体变体

### 统一变体维度

每个变体至少支持：

- `scope_type`
- `episode_start / episode_end`
- `story_phase`
- `state_tags`
- `priority`
- `is_default`

三类资产的状态重点如下：

- 人物：服装、发型、妆容、情绪、身体状态、剧情阶段
- 场景：时间、天气、光线、陈设状态、破坏程度、剧情痕迹
- 道具：完整度、污损状态、使用状态、附着物、剧情状态

### 统一镜头绑定优先级

镜头绑定优先级统一为：

1. 镜头显式绑定变体
2. `shot_variant`
3. `scene_variant`
4. `episode_default`
5. `base_identity`

任何镜头都必须能回答：

- 当前绑定的是哪个人物变体
- 当前绑定的是哪个场景变体
- 当前绑定的是哪个道具变体
- 当前主参考图和锁定参考图分别是哪一张
- 当前是显式绑定、规则命中还是回退命中

### 统一提示词权威源机制

人物、场景、道具的提示词统一分成三层：

1. `confirmed_prompt_raw`
   - 用户确认过的权威原文
   - 不能被模板重渲染、迁移脚本、批量重编译自动覆盖
2. `structured_variant_fields`
   - 供系统编译、变体匹配、镜头绑定使用的结构化字段
3. `rendered_prompt_preview`
   - 系统按统一模板骨架渲染出的预览稿

必须遵守：

- 禁止用 `rendered_prompt_preview` 覆盖 `confirmed_prompt_raw`
- 人物、场景、道具都必须保留用户确认原文
- 状态信息可以按变体变化，但不能静默改写用户已确认的权威稿

### 对现有模块的直接要求

对资产中心：

- 必须展示主档案、变体列表、每个变体下的参考图、变体影响镜头
- 必须支持人物、场景、道具统一的多变体管理

对镜头工作台：

- 必须显示镜头当前绑定的具体人物 / 场景 / 道具变体
- 必须显示本次编译实际引用的具体变体与主参考图

对提示词编译体系：

- 静态提示词、运动提示词、人物定妆提示词、场景提示词、道具提示词都必须引用“变体”
- 不得只引用主资产名称或摘要字段

### 补充验收标准

新增验收标准如下：

1. 同一人物可存在多套跨集、跨阶段、跨状态变体，并按镜头正确引用
2. 同一场景可存在多套时间 / 天气 / 光线 / 陈设状态变体，并按镜头正确引用
3. 同一道具可存在多套完整度 / 污损 / 使用状态变体，并按镜头正确引用
4. 每个变体都可挂载多张参考图，并区分默认、锁定、候选
5. 删除某个变体参考图后，镜头 readiness、风险提示、引用状态实时更新
6. 用户确认过的资产最终提示词原文不会被系统模板自动覆盖

## 补充蓝图：分镜视频生成链路语义校准

### 现状问题

- 产品语义希望做“已采纳首帧驱动的视频生成”，但当前实现里首帧更多只是 `source_asset_id` 元数据
- provider 适配层实际更依赖 `reference_images`，容易把静态资产参考图误当作 `first_frame`
- 前端发起视频生成时缺少显式输入，导致“首帧、参考图、运动提示词、模型参数”的责任边界不清

### 目标语义

- 分镜视频必须以“当前镜头已采纳首帧”为唯一首帧输入来源
- 人物、场景、道具参考图作为独立 `reference_asset_ids / reference_images` 输入，不与首帧混用
- 运动提示词使用当前镜头锁定或当前生效的 `visual_prompt_motion`
- 负向提示词使用当前镜头锁定或当前生效的 `visual_prompt_final`
- 结果资产必须可追溯“用了哪张首帧、哪些参考图、哪版运动提示词、实际走了什么模型 task_mode”

### 实施要求

- 在服务端建立统一的 `video_generation_context` 组装层，显式解析：
  - `first_frame_asset_id`
  - `first_frame_url`
  - `reference_asset_ids`
  - `reference_images`
  - `prompt_motion`
  - `negative_prompt`
- provider 适配层按统一语义翻译，而不是自行猜测首帧：
  - 优先 `image_to_video`
  - 次选 `reference_to_video`
  - 最后才允许 `text_to_video`
- 前端在用户点击“生成视频”前，必须让用户看见本次生成将使用：
  - 哪张首帧
  - 哪些参考图
  - 哪版运动提示词
  - 哪个视频模型
- 视频生成结果 metadata 必须补齐：
  - `firstFrameAssetId`
  - `firstFrameUrl`
  - `referenceAssetIds`
  - `referenceImages`
  - `promptMotion`
  - `negativePrompt`
  - `providerTaskMode`

### 验收标准

1. 任一视频生成请求都能明确指出“使用的首帧是谁”
2. provider 收到的 `first_frame` 必须来自 adopted 首帧，而不是静态资产参考图
3. provider 收到的 `reference_image_urls` 必须来自静态资产引用，不混入首帧
4. 任一生成后的视频版本都能追溯“首帧、参考图、运动提示词、负向提示词、模型模式”
5. 前端在无 adopted 首帧时禁用“生成视频”，而不是点击后才报错

## 1. 目标定义

本清单用于把“产品重构蓝图”推进到可上线判断阶段。

这里的“上线”分为两层：

- 内测上线：服务项目团队自身真实生产，可接受少量人工兜底
- 生产级上线：能够稳定承载真实项目生产，不依赖频繁人工修补，不因常见异常中断主链路

当前判断：

- 正式工作台整体达成率：约 75% - 82%
- 生产级可上线达成率：约 60% - 70%

## 2. 冲刺分级

1. 主链路完整跑通  
从 `内容准备 -> 改编方向 -> 剧本 -> 分镜 -> 资产 -> QA -> 导出` 至少跑通 3 个真实项目。

当前状态：已具备可复用的真实浏览器业务流 E2E fixture，并建立 5 个真实项目的非破坏性回归样本库；下一步需要继续补充更多可回滚写入型真实样本，并把真实样本中的资产继承/任务恢复异常纳入固定验收。

2. 分镜提示词质量达标  
静态提示词、运动提示词达到既定结构和质量标准，且可稳定引用资产与状态。

2.1 分镜生成可拍性治理（P0 子项）
分镜不能只满足字段完整和提示词长度，还必须在目标时长内可执行，并能判断应优化、延长还是拆镜。

当前状态：方案已落档并开始实现。已新增纯函数 `core/shot_executability.py`，接入 `core/prompt_ir.py`，可输出 `action_count`、`recommended_max_actions`、`executability.status`、可拍性 findings 及延长/删减/拆镜建议；当前尚未阻断数据库落库和真实提交。下一步接入 `Shot Intent Planner`、`Action Timing Planner` 的 LLM JSON 字段，并把校验结果落入 Shot Schema、正式工作台和真实视频提交门禁。

3. 多变体资产继承稳定  
人物、场景、道具在跨集、跨阶段、跨镜头状态下，能够稳定命中正确版本。

4. 真实生成恢复链路可用  
失败任务、重编后继续生成、按原始输入重发、按最新状态重生成都必须可追踪、可恢复、可解释。

5. QA 放行机制成型  
不是只有 QA 页面，而是有明确的阻塞、修复、复检、放行标准。

6. 数据脏值与乱码系统清理  
正式工作台各核心模块不再随机暴露乱码、转义串、问号占位或历史脏字段。

### P1：强烈建议上线前完成

1. 模型管理彻底收口  
统一模型命名、别名、能力说明、默认值与适配层行为。

2. 资产中心闭环增强  
参考图预览、删除、默认、锁定、回写、镜头绑定和 stale prompt 修复动作全部顺手可用。

3. 镜头工作台提交前确认  
生成首帧/视频前，用户能看清本次实际提交的提示词版本、参考图、首帧、模型和模式。

4. 导出中心更接近交付标准  
所有阻塞项可见、可回跳、可追溯。

## 4. 每项验收标准

### 4.1 主链路完整跑通

验收标准：

- 至少 3 个真实项目从内容准备走到导出中心
- 每个阶段都有明确输入、输出和下一步建议
- 不出现必须人工改库或改 JSON 才能继续的断点
- 真浏览器完整操作可复现
- 自动化层面至少包含 `npm run e2e:business`，并保留 smoke/QA 专项作为补充

### 4.2 分镜提示词质量达标

验收标准：

- 抽检不少于 30 个镜头
- 静态提示词包含人物、场景、道具、状态、时间、机位、质感等必要信息
- 运动提示词能表达明确的镜头运动和动作变化
- 每个镜头有唯一核心动作，并有与 `duration` 对齐的 `action_beats[]`
- 4 秒镜头默认不超过 2～3 个连续动作；超载镜头必须进入 warning/blocked 或等待用户确认覆盖
- 可拍性校验能区分提示词可优化、镜头应延长、镜头应拆分三类结论
- 起止状态能够承接前后镜头，且动作、构图和镜头运动不存在明显冲突
- 正确继承资产版本与分镜状态
- 不再出现大面积模板化、空泛化、错误角色、错误服装、错误场景
- 导演分镜语言、标准机器提示词、模型导出和 API 提交四层分离
- H3 / WebUI 导出包含可观察动作时间线、环境声、非画内配乐、参考图/首帧使用策略

### 4.3 多变体资产继承稳定

验收标准：

- 人物支持基础定妆、分集默认、分镜精调三层稳定引用
- 场景与道具支持多版本命名、筛选、引用和回看
- 同一镜头引用的资产版本可解释、可追踪
- 真浏览器下，资产中心与镜头工作台显示一致

### 4.4 恢复链路可用

验收标准：

- 任务中心能显示真实任务链路、版本关系、输入摘要、失败原因
- 支持刷新、继续回收、按原始输入重发、按最新状态重生成
- 恢复后状态能回写到镜头工作台和资产中心
- 不出现恢复后任务来源不明、状态错乱、版本丢失

### 4.5 QA 放行机制成型

验收标准：

- 每个 QA 问题都可落到具体修复动作
- QA 生命周期至少包括 `open / in_progress / resolved / wont_fix`
- 修复后可复检，可回写状态
- 导出中心能读取真实 QA 阻塞而不是仅看文案猜测

当前状态：

- 2026-08-26 已让导出中心读取 `/api/books/{book_id}/qa/workbench`，并优先按 QA workbench 的生命周期状态判断交付阻塞。
- `recheck_passed / resolved / closed / accepted / workflow_status=resolved / workflow_status=wont_fix` 视为已放行，不再阻塞导出。
- `open / in_progress / fixing / fixed / rechecking` 等仍视为可执行待处理项，导出中心会显示 `QA 待处理 X 项` 并回跳 QA 修复。
- 旧 `qaEntries.error_count` 仅作为 workbench 摘要缺失时的兼容兜底。
- 后端 `export-records` 与 `export-pdf` 已接入同一 QA lifecycle gate：前端误传 completed 时会被强制降级为 blocked；PDF 直出遇到 QA 阻塞返回 `409 qa_blocked`。

### 4.6 数据脏值与乱码系统清理

验收标准：

- 正式工作台主要模块不再出现 `\uXXXX` 裸转义
- 不再出现明显乱码或 `???`
- 历史项目中常见旧数据能正常展示
- 对典型脏值建立回归测试

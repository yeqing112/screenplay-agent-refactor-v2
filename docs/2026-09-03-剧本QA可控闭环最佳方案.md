# 剧本 QA 可控闭环：从“整段重写”到“锚定编辑 + 可验收”

> 日期：2026-09-03
> 定位：把 QA 修复复杂度收口成可终止、可合并、可验收的闭环，不继续堆启发式规则。
> 前置：本方案复用分镜层已有的 `ShotIR.action_beats` 与 `structured_shot` 哲学，上推到剧本层。

## 1. 问题重构

“QA 后重写”之所以绕，不是某函数写得差，而是五个前提叠加：

1. 剧本是扁平文本，QA 只能报行号；任何一次修改都会让后续行号整体平移，导致“已定位”失效。
2. 不同 QA 问题重叠指向同一段（动机 / 钩子 / 节奏都在一个结尾块），分开修互相冲突。
3. 模型输出不可靠：可能原样复读（no-op）、可能整场重写、可能把另一位刚删掉的东西写回去。
4. 复检＝重跑全套 QA，会不断挑新毛病，目标无边，循环不终止。
5. 主观项没有可验证的通过条件，自动化的性价比在这里归零。

结论：只要围绕“文本 + 行号 + 整段替换”优化，复杂度无解，必须换掉这三个前提。

## 2. 方案全景

| 痛点 | 解法 | 复用/新增 |
|------|------|-----------|
| 行号平移 | 剧本→结构化 beat，稳定 beat_id 锚点 | 复用 `ShotIR.action_beats`，新增剧本层 beat 索引 |
| 重叠冲突 | 修复输出「编辑操作数组」，合并/校验器应用 | 新增编辑操作协议 + 冲突检测 |
| 模型不可靠 | 锚定 diff + 指纹校验 + no-op/越界拒绝 | 复用 `_qa_fix_patch_has_change`、`decision_draft` |
| 循环不终止 | 每题一个可判定 resolution_criteria，复检只判 target | 新增通过条件评判器 + scoped harness |
| 主观烧钱 | 结构/矛盾自动，主观转人工队列 | 按 rule_family + confidence 路由 |

四层拓扑：

```
剧本文本
  └─(确定性编译)→ Beat 索引：scene → beat_id → {kind, speaker, content, fingerprint}
                    QA 只挂 beat_id，不挂行号
  └─(QA 输出)→ QA 问题 {beat_ids, rule_family, description, resolution_criteria}
                    每题带可判定通过条件
  └─(LLM 修复)→ 编辑操作数组 [{op, beat_id, old_text, new_text}]
                    锚定、可合并、带片段指纹
  └─(应用)→ 合并器批量 apply → 新剧本版本（保留快照/回滚）
  └─(harness)→ 只 re-validate N 个 target 的 resolution_criteria → 通过即止
```

## 3. Beat 索引与锚点

### 3.1 Beat 粒度

在既有 `## 场景N：名称` 标题与 `**[动作开始]/[动作结束]**`、`**[视觉证明N]**`、`**[人物入场]**` 标记上做确定性切分：

- 场景级：以 `## 场景N` / `[场景结束]` 为边界（复用现有 `_extract_scene_blocks`）。
- 场景内 beat：
  - 一条对白（`**角色**` 引言行）→ 1 beat。
  - 一段连续舞台指令/动作（被 `**[动作开始]**`、空行或视觉证明包裹）→ 1 beat。
  - 一个 `[视觉证明N]` + 其下一行特写 → 该视觉证明 beat。

### 3.2 Beat 结构

```python
@dataclass
class ScriptBeat:
    beat_id: str        # "ep1-s2-b03"（稳定，不随行号变化）
    beat_index: int     # 场景内序号
    scene_no: int
    scene_name: str
    kind: str           # dialogue / action / visual_proof / heading
    speaker: str        # dialogue 用
    content: str        # beat 原文
    start_line: int     # 仅作当前版本瞬时定位，不作稳定锚点
    end_line: int
    fingerprint: str    # sha256(content)[:24]
```

`beat_id` 是唯一稳定锚点。`start_line/end_line` 仅供 UI 高亮当前版本文本。每次脚本变更后重建整个 beat 索引（幂等、确定性），旧索引存入版本快照以支持回滚。

### 3.3 为什么能根治行号平移

QA 与修复都只认 `beat_id`。修改一段文本 → 该 beat 的 `fingerprint` 变化 → 后续 beat 的 `start_line` 自动重算，但 `beat_id` 不变。于是“改到哪个 beat”永远稳定，跨版本不再依赖行号。

## 4. QA 锚点协议

QA agent 输出与现有 `QAIssue` 兼容，但新增字段：

```json
{
  "issue_key": "qa-ep1-...",
  "type": "motivation",
  "rule_family": "character_state_transition",
  "severity": "high",
  "beat_ids": ["ep1-s2-b11", "ep1-s2-b12"],
  "description": "林晚通讯更像受指派的特工，与继承人/重生者设定冲突。",
  "resolution_criteria": {
    "kind": "forbidden_phrases",
    "beat_ids": ["ep1-s2-b11", "ep1-s2-b12"],
    "forbidden": ["目标确认", "物品已转移", "请求下一步指令"],
    "required_hint": ["钟楼", "记忆", "裂痕"]
  }
}
```

`resolution_criteria` 是可判定谓词，有三种形态：

- `forbidden_phrases`：目标 beat 内不得出现 `forbidden`，且应包含 `required_hint` 至少一项。
- `contains_required`：目标 beat 必须包含 `required` 子串（结构补全类）。
- `structure_present`：目标 beat 必须存在（用于“某视觉证明缺失”类）。

缺失 `beat_ids` 的旧数据，用既有“场景号 + 位置限定词 + 场景内命中”降级推导；推导不出可靠 beat 时只能走“策略型”或“转人工”，绝不进入可写路径。

## 5. 编辑操作协议

### 5.1 输出格式

LLM 不再输出整段替换，而是输出操作数组：

```json
{
  "decision": "ready_for_review",
  "edits": [
    {"op": "replace", "beat_id": "ep1-s2-b11", "new_text": "**“钟楼布局与记忆一致，但钟面裂痕是新的变数。请求下一步指令。”**"},
    {"op": "insert_after", "beat_id": "ep1-s2-b12", "new_text": "**“你外婆的死，不是意外。钟楼里，有人在等你。”**"},
    {"op": "delete", "beat_id": "ep1-s1-b05"}
  ],
  "rationale": "..."
}
```

### 5.2 每条操作的硬校验（应用前）

- `beat_id` 必须存在于当前冻结的 beat 索引。
- `op=replace` 时，当前 beat 的 `fingerprint` 必须与证据包冻结时一致（不一致说明文本已变，标记 stale 拒绝）。
- `new_text` 非空且与原文归一化后不相等（no-op 拒绝）。
- `delete/insert` 不得删除或插入会破坏结构稳定性的标记（如 `[场景结束]`、场景标题）。
- 操作数上限（如 ≤ 8），防止大规模改写。

### 5.3 合并器

对同一 `beat_id` 的多个操作、或跨版本行号平移，按 beat_id 归并 + 单调索引应用：

1. 按 `beat_id` 归并操作；同一 beat 多 op 先判定是否矛盾（同一 beat 同时 replace+delete → 冲突标记）。
2. 按 beat 顺序应用，重算行号；`insert_after beatX` 紧跟其后插入。
3. 应用后重建 beat 索引，校验受影响 beat 的指纹是否达到 `resolution_criteria` 预期。
4. 出现重叠/矛盾 `beat_id` → 返回 `conflict`，不应用，转人工。

这是 CRDT / three-way-merge 的轻量版；未来并发编辑需求加重时，可平滑替换为 Yjs/Automerge 或 `diff-match-patch`。

### 5.4 与现有版本/回滚衔接

应用编辑操作数组即产生一次 `ScriptVersion`（`change_type=qa_fix`），沿用现有 `content_before/after/diff_text`、状态快照与回滚链路。每次应用都把旧 beat 索引存入版本元数据，回滚时同步回滚索引。

## 6. 通过条件与 scoped harness（终止性）

复检不再重跑全套 QA 挑新毛病，而是：

1. 从证据包取 `target_issue_keys`（本轮要修的 N 个）。
2. 对每题读取 `resolution_criteria`，用 judge（规则优先，复杂项可用 judge LLM）判断是否满足。
3. 满足 → 标记 `resolved`；不满足 → 返回 `needs_refinement`（可再给一轮，但不自动无限循环）。
4. 只对 target 集断言；非 target 的新建议转人工队列，不当作阻塞。

```
for issue in targets:
    ok = evaluate(issue.resolution_criteria, current_script)
    if ok: issue.status = "resolved"
    else: issue.status = "needs_refinement"; route_to_human_if_subjective(issue)
```

这给出确定性终止条件：`target 全部通过` 即停，不再以“分数变好/无新问题”这类无界目标为准。

## 7. 自动化 vs 人工边界

| rule_family / 类型 | 处理 |
|--------------------|------|
| 结构缺失、场景结束标记、明显矛盾、截断、可判定短语冲突 | 自动化（编辑操作 + 判定条件） |
| 动机深度、节奏偏好、钩子“更震撼”、道具属性模糊等主观项 | 转人工定稿队列，不自动改写 |

路由：`rule_family in STRUCTURAL SET` 且给出可判定 `resolution_criteria` → 自动；否则 `confidence/确定性低` → 人工。人工改完仍走同一“改 beat → 应用 → 版本快照”链路，保证可回滚。

## 8. 兼容与迁移

- 不新增表：`beat_id`、`resolution_criteria` 作为 `QAIssue.meta_info` 与新 `ScriptVersion.meta_info` 内字段；Beat 索引是派生 JSON，由当前剧本确定性重建。
- 旧 `QAIssue` 无 `beat_ids` → 用现有定位逻辑降级为策略/人工，不误写。
- 现有 `DecisionPacket` / `decision_draft` / `llm-draft` 保留为“证据包 + 受控调用”，编辑操作数组作为其 `proposal.edits` 的新结构。
- 现有 `apply-fix`/`preview-fix` 保留兼容旧整段替换；新链路走 `apply-edits`。

## 9. 落地阶段与验收

### 阶段 A：剧本 Beat 索引
- 确定性解析 `## 场景N` + `[场景结束]` + `[视觉证明N]` + 对白/动作，产出 `ScriptBeat[]`。
- 验收：新样本某集索引出的 beat 数与手工清点一致；beat_id 两次修改间稳定；指纹随内容变化。

### 阶段 B：QA 锚点 + 判定条件
- QA 输出 `beat_ids` + `resolution_criteria`（forbidden/contains/structure）。
- 验收：每题能定位到唯一 beat；`resolution_criteria` 可被 judge/规则判定。

### 阶段 C：编辑操作协议 + 合并器
- 新增 `apply-edits`；校验 beat 存在、指纹匹配、no-op、结构标记保护、操作数上限、冲突拒用。
- 验收：重叠/矛盾返回 `conflict`；合法操作产生版本 + 快照；回滚还原索引。

### 阶段 D：scoped harness
- 复检只评估 target 的 `resolution_criteria`；通过即 `resolved`，非 target 建议转人工。
- 验收：给定 N 个 target，修复后断言全部通过即停；不再以“无新问题”为准。

### 阶段 E：路由 + 人工队列
- `rule_family` 路由自动化/人工；人工队列沿用 beat 编辑链路。
- 验收：主观项不进入自动改写；结构项自动闭环。

## 10. 明确不做什么

- 不做整集重写，或跨越单场景的整段替换作为自动修复单位。
- 不把“更好看 / 更有冲击 / 更顺”这类主观项纳入自动改写（无判定条件）。
- 不新增任何书号、角色名、关键词特例；判定都基于 beat 结构、指纹、规则族。
- 不替代“人在剧本编辑器里直接改”这种最省路径；当无批量/审计需求时，人工编辑仍是最优解。

## 11. 结论

换掉三个前提——**文本 → beat 结构、行号 → beat_id 锚点、整段替换 → 锚定编辑操作**——是复杂度真正的下降点。再加**每题一个可判定通过条件**，循环就从“无限逼近”变成“可终止、可验收”。这套方案复用分镜层已有的 `ShotIR.action_beats` / `structured_shot` 思想，既通用，又最小偏离现有架构。

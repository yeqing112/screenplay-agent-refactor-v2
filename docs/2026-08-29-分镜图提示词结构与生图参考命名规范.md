# 2026-08-29 分镜图提示词结构与生图参考命名规范

## 背景

本轮修复的核心问题是：分镜图提示词不能再把人物定妆设定板、六视图、参考图模板等内容混入当前镜头首帧画面。用户可编辑的是“导演分镜语言”，系统提交给生图模型的应是经过结构化编译后的“标准化分镜图提示词”。

## 分镜图提示词结构

内部统一采用 `storyboard_image_prompt_sections_v1`：

1. `frame_focus`：画面定格。描述当前首帧是什么画面、景别、场景和开场状态。
2. `asset_anchors`：资产锚点。明确场景、人物、道具分别对应哪个参考资产和 `@引用名`。
3. `composition`：构图关系。描述主体、场景、道具在画面里的相对关系。
4. `frozen_action`：当前帧动作。只写首帧定格动作，不写完整视频过程。
5. `asset_visual_facts`：资产视觉事实。只继承当前镜头需要的外观、空间、材质、光线、状态事实。
6. `lighting_emotion`：光线与情绪。描述光源、色温、明暗关系和情绪基调。
7. `constraints`：一致性与禁止项。保持参考图身份、服装、发型、场景布局和道具状态，禁止新增未声明人物、道具、文字、水印和设定板排版。

最终提交给模型的 `visual_prompt_static` 仍应是自然中文画面描述，不直接输出字段清单。字段清单用于系统审计、UI 展示、导出和后续多模型适配。

## 资产信息进入提示词的原则

- 资产锚点负责“告诉模型谁是谁”：例如 `场景：便利店收银台（@便利店收银台）`、`人物：林小夏（@林小夏）`。
- 资产视觉事实负责“告诉模型当前画面要继承什么”：例如收银台空间结构、冷白荧光灯、人物发型和服装、道具材质与状态。
- 不把资产参考图生成模板原样带入分镜图提示词，例如“人物定妆设定板”“六个视角”“上排脸部特写”“下排全身展示”等。
- 不只写“参考 @某人物 / @某场景”，必须自然吸收关键视觉事实，否则模型只知道有参考图，不知道在当前镜头里怎么用。

## 常见生图模型参数调查摘要

### GPT Image 2 / PoYo

- `model`: `gpt-image-2` 文生图；`gpt-image-2-edit` 图像编辑。
- `prompt`: 图像生成文本，PoYo 文档标注上限 20,000 字。
- `quality`: `low / medium / high`。
- `size`: `auto`、常见比例如 `1:1 / 16:9 / 9:16 / 21:9`，或自定义 `WIDTHxHEIGHT`。
- `resolution`: `1K / 2K / 4K`；自定义尺寸要求 `2K` 或 `4K`，宽高需能被 16 整除，并受最大边长和总像素限制。
- `image_urls`: `gpt-image-2-edit` 必需；PoYo 文档说明支持多张参考图。

### OpenAI Images API

- 常见核心参数为 `prompt / model / size / quality / n / background / output_format / output_compression / moderation / stream`。
- GPT Image 系列支持 `low / medium / high / auto` 质量、`png / jpeg / webp` 输出格式、透明/不透明背景等参数。
- GPT Image 2 支持自定义 `WIDTHxHEIGHT`，宽高需能被 16 整除，并受比例、边长和像素限制。

### Midjourney / WebUI 类平台

- 图像参考通常不是一个结构化 JSON 字段，而是图片 URL 加在 prompt 中。
- 常见参数包括 `--ar` 比例、`--iw` 图片参考权重、`--cref` 人物参考、`--cw` 人物参考权重、`--sref` 风格参考、`--sw` 风格权重、`--seed`、`--no`。
- 对这类平台，系统导出时应把每张参考图按用途分组，用户才能正确粘贴到 WebUI。

### Stable Diffusion / ComfyUI / FLUX 类链路

- 常见参数包括 `prompt / negative_prompt / width / height / aspect_ratio / steps / guidance 或 CFG / seed / sampler / scheduler / denoise 或 strength / reference image weight`。
- 参考图通常通过节点输入、ControlNet、IP-Adapter、img2img 或模型专用 `image_url` 字段传入；“参考名”多数是工作流内部标签，不一定是 provider 的正式字段。

## 参考名命名规范

结论：多数 API 不强制要求“参考名”，但影视生产必须内部定义稳定命名，否则多人物、多道具、多版本时很容易错绑。

本项目采用双层命名：

1. 稳定机器 ID：`reference_asset_id = ref-72`。用于数据库、任务、回收、迁移和 API payload。
2. 人类可读锚点：`reference_token = @便利店收银台`。用于导演语言、提示词、WebUI 导出和人工核对。

推荐 payload 元数据：

```json
{
  "reference_asset_id": "ref-72",
  "asset_type": "scene",
  "asset_id": "159",
  "asset_name": "便利店收银台",
  "reference_name": "@便利店收银台",
  "reference_label": "@便利店收银台",
  "reference_role": "scene",
  "reference_purpose": "background_layout_lighting",
  "weight": 1.0,
  "image_url": "https://..."
}
```

命名规则：

- `reference_token` 默认使用 `@资产名`，例如 `@林小夏`、`@神秘男人`、`@便利店收银台`、`@旧照片`。
- 同名资产必须加范围后缀，例如 `@林小夏-基础定妆`、`@林小夏-镜头003`、`@便利店收银台-夜班`。
- 角色参考优先表达身份与外观一致性；场景参考优先表达空间布局与光线；道具参考优先表达形制、材质和状态。
- API 提交通常只需要 URL；WebUI 导出需要同时显示 `reference_token + role + purpose + weight`，方便用户手工粘贴和判断。

## 本轮落地

- `core.model_adapter.StoryboardChineseAdapter` 新增 `static_prompt_sections` 结构化输出。
- `_compile_storyboard_prompts` 将该结构写入 `prompt_compile_context.model_adapter.static_prompt_sections`。
- 参考图 payload 新增 `reference_name / reference_label / reference_role / reference_purpose / weight`，便于 API 和 WebUI 双通道导出。
- `prompts/storyboard/prompt_compiler.txt` 已补规则：LLM 必须理解结构化基线，但最终 `visual_prompt_static` 仍输出自然中文，不原样输出字段名。

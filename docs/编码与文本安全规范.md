# 编码与文本安全规范

更新时间：2026-08-03

## 1. 目标

本规范用于杜绝以下问题再次进入主链路：

- 中文乱码
- JSX / 字符串因编码问题损坏
- 规则文档不可读
- 前端页面出现编码错乱文案

它适用于：

- 前端源码
- 后端源码
- Markdown 文档
- 验收记录
- 提示词模板与提示词编译相关文本

## 2. 强制规则

### 2.1 统一编码

- 所有源码与新文档统一使用 `UTF-8`。
- 默认使用 `UTF-8 without BOM`。
- 不允许混用 GBK、ANSI、UTF-16 作为项目长期存储格式。

### 2.2 禁止在污染文件上继续堆中文改动

如果文件已经出现以下任一情况：

- 明显乱码
- 编辑器正常、终端异常
- 终端正常、页面异常
- 模板字符串、引号、JSX 标签被污染

则该文件进入“编码污染状态”。

进入污染状态后，禁止继续做大段中文增量编辑，必须改用以下方式之一：

1. 整文件重建
2. 先改为 ASCII 安全文案，再回填中文
3. 抽离文案到独立常量文件

### 2.3 逻辑改动与大段文案改动分离

高风险文件中，不允许同时进行：

- 复杂逻辑修改
- 大段中文文案调整
- 编码修复

必须拆成多步闭环。

### 2.4 规则文档优先健康

如果 `AGENT.MD`、蓝图、阶段任务、验收记录本身出现乱码，优先修复文档，再继续开发。

## 3. 推荐工作流

### 3.1 修改前

先确认：

1. 文件编码是否健康
2. 文件是否已经出现 mojibake
3. 是否需要整文件重建而不是局部补丁

### 3.2 修改中

- 小步提交
- 避免在污染文件中反复 patch 中文字符串
- 必要时先用 ASCII 占位文案

### 3.3 修改后

至少执行：

1. 相关测试
2. 最小编译验证
3. 全量构建
4. 真页面验收

未通过上述步骤，不得视为完成。

## 4. 高风险信号

出现以下任一信号，立即暂停局部修补：

- 终端里大量出现 `闂`、`鍒`、`鎴`、`妫`、`鏈€`、`褰撳墠` 这类异常片段
- 原本正常的中文被拆成高频异常字串
- esbuild / tsc 报 `unterminated string literal`
- JSX 报 `The character \">\" is not valid inside a JSX element`
- 文本显示和源码预期不一致

## 5. 修复策略

### 策略 A：整文件重建

适用：

- 文件已大面积污染
- JSX / 引号结构已经损坏
- 局部 patch 成本高于重建

要求：

- 保留原接口
- 保留关键功能
- 先恢复可编译、可运行、可验收

### 策略 B：ASCII 过渡

适用：

- 当前必须快速恢复编译
- 污染集中在文案层

要求：

- 先用稳定 ASCII 或短中文占位
- 构建通过后再统一回填正式文案

### 策略 C：文案抽离

适用：

- 文件逻辑复杂
- 文案频繁变化
- 同模块存在多处重复展示文本

要求：

- 抽离常量
- 降低未来再次污染的编辑面

## 6. 交付验收标准

编码治理类修复完成后，必须同时满足：

- 相关测试通过
- 前端构建通过
- 真页面文案可正常显示
- 对应验收记录已写入
- 蓝图与阶段任务已同步

## 7. 当前执行要求

从 2026-08-03 起，后续所有实现默认遵循本规范。

若再次发现编码污染：

- 不允许只在对话中解释
- 必须给出修复动作
- 必须落到文档与验收记录

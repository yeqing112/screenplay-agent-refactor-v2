# LibTV 化融合重构计划

更新时间：2026-08-22

## 1. 融合目标

本项目后续产品形态，不再只是“若干工作台的集合”，而是要继续向 LibTV 风格靠拢：

- 更强的连续创作体验
- 更强的节点化上下文组织
- 更自然的创作与生产联动
- 更少的页面割裂感

但本项目不会照搬 LibTV，而是做“LibTV 创作体验 + AI 短剧生产系统”的融合。

## 2. 为什么要融合

当前正式产品工作台已经解决了很多“生产组织问题”，比如：

- 主模块结构
- 任务恢复
- 资产与镜头联动
- QA 与交付入口

但它在“创作体验”上仍然偏工作台式，主要问题是：

- 创作上下文还比较分散
- 画布更像联动导航，而不是连续创作空间
- 用户需要在镜头、资产、任务之间跳转理解关系

LibTV 化的价值，在于把这些关系进一步前置成“同一创作空间里的可操作对象”。

## 3. 融合原则

### 保留的部分

- 正式产品工作台的主链路
- 真实项目数据接入
- 资产、镜头、QA、任务、导出的生产闭环
- 任务中心恢复链路

### 强化的部分

- 创作画布继续作为正式工作台内的 LibTV 化创作视图
- 节点不只是展示关系，要能承载连续创作动作
- 画布与镜头工作台之间要共享同源运行态与上下文

### 不做的部分

- 不把全部生产逻辑塞回一个巨型页面
- 不为了“像 LibTV”而牺牲正式生产治理
- 不回退成单纯视觉关系图

## 4. 目标产品结构

融合后的结构仍以正式产品工作台为主骨架：

1. 项目控制台
2. 内容准备
3. 改编方向
4. 剧本工作台
5. 镜头工作台
6. 创作画布
7. 资产中心
8. QA 修复
9. 任务中心
10. 导出中心
11. 模型管理

其中，创作画布承担 LibTV 化演进的主要载体。

## 5. 创作画布的产品意义

创作画布不是简单关系图，也不是旧原型的视觉包装。

它的正式职责应该是：

- 把剧本、镜头、资产、执行结果放进同一创作上下文
- 允许用户围绕当前集、当前镜头、当前任务持续推进
- 让“查看关系”升级为“直接创作、直接恢复、直接修复”

### 画布至少要支持的核心动作

- 从节点进入镜头提示词编译
- 从节点进入首帧生成 / 视频生成
- 从节点查看待回收任务与最近执行
- 从节点进入关联资产
- 从节点进入 QA 修复与交付判断

## 6. 当前融合进度

截至 2026-08-22，已经完成的部分：

- 创作画布已接入真实项目数据
- 已具备按集、按镜头查看节点的基本能力
- 已接入镜头级运行态摘要
- 已接入首帧 / 视频等执行动作
- 已完成与任务中心、镜头工作台的基础上下文回跳
- 前端已完成单一正式工作台收敛，创作画布不再作为独立 Beta 控制台理解
- 正式工作台真实业务流 E2E 已覆盖跨模块浏览、提示词锁定、验收记录、QA 修复和脚本回滚

但尚未完成的部分仍然很关键：

- 节点式连续创作体验仍不够强
- 画布还没有真正成为“主创作空间”
- 多节点协作与批量创作编排仍不足

## 7. 阶段任务

## 阶段 L1：画布从展示走向操作

### 任务

- [x] 真实项目建图
- [x] 单镜头执行动作接入
- [x] 节点运行态摘要接入
- [x] 任务中心 / 镜头工作台上下文回跳接入

### 验收标准

- 用户在画布中能围绕单镜头直接执行关键动作
- 画布显示的运行态与镜头工作台、任务中心一致

## 阶段 L2：画布成为连续创作空间

### 任务

- [ ] 在节点详情中持续补齐正式创作动作
- [ ] 强化多节点筛选、批量推进、状态比较
- [ ] 让“下一步建议”从静态提示升级为可直接执行的编排动作

### 验收标准

- 用户不必频繁切页，也能在画布里连续推进多个镜头
- 画布不只是查看入口，而是可执行生产空间

## 阶段 L3：画布与生产治理统一

### 任务

- [ ] 让资产、QA、任务、交付状态在画布里形成统一视图
- [ ] 让画布成为正式工作台里的高频主入口之一
- [ ] 保证画布动作不会绕开正式任务恢复、QA、交付治理

### 验收标准

- 画布与正式工作台各模块共享同一套状态源
- 画布上的动作可以被任务中心、QA、交付链路正确追踪

## 9. 决策结论

这次融合是正确选择，但前提是：

- 先保住正式生产闭环
- 再让画布逐步吃下创作高频动作
- 不把 LibTV 风格理解成“只做一个图”

后续推进原则可以概括为一句话：

`用 LibTV 化的创作体验，承载正式产品工作台的生产闭环。`

## 10. 2026-08-22 单一工作台后的近期任务

1. 把创作画布文档与用户可见命名全部统一为 `创作画布`，历史验收记录中的 `Beta` 只作为当时名称保留。
2. 将 `npm run e2e:business` 纳入画布相关大改后的固定回归，避免画布动作破坏正式工作台主链路。
3. 继续把画布动作接入任务中心恢复谱系，不新增绕开正式任务治理的本地假状态。
4. 在至少 3 个真实项目上验证 `创作画布 -> 镜头/资产/QA/任务/导出` 的回跳与状态一致性。
